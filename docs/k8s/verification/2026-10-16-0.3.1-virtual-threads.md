# Virtual threads on kind, 0.3.1

Checked 2026-10-16 at `ba589da` (`rel-0.3.1`), on the kind fleet brought up with
`./k8s/kube.sh up --no-build` from the images the release gate built (`ezeebit/<svc>:0.3.1`, every pod
at CPU limit 2). One deposit of 100.00 ZAR (201) and one conversion of 50.00 (201, COMPLETED) were
sent through the gateway with the sweep's own `deposit` and `convert` helpers from `k8s/sweep/lib.sh`.

Spring's default console pattern prints the thread name cut to its last 15 characters, so Tomcat's
virtual-thread executor (`tomcat-handler-N`) prints as `omcat-handler-N`, and its platform pool
(`http-nio-<port>-exec-N`) would print as `...-exec-N`. Per pod, from `kubectl logs`:

| Pod | `handler-N` lines (virtual) | `exec-N` lines (platform) |
|---|---:|---:|
| config-svc-56485686b5-dzrvr | 17 | 0 |
| conversion-svc-78fb55d597-59pcb | 5 | 0 |
| conversion-svc-78fb55d597-kmvc6 | 3 | 0 |
| eureka-svc-8569687547-x75bf | 9 | 0 |
| gateway-svc-5c954f5b89-hr5g6 | 4 | 0 |
| gateway-svc-5c954f5b89-l4sgz | 4 | 0 |
| ledger-svc-54db46487b-j2pd4 | 4 | 0 |
| ledger-svc-54db46487b-sbhcp | 3 | 0 |

The deposit itself is one of the ledger lines:
`[omcat-handler-7] ... i.e.l.service.deposit.DepositService : deposit POSTED in ZAR`.

What this does not show: the platform-thread column has no positive control from a 0.3.0 pod in the
same run, so the zero rests on Tomcat's documented names rather than on a side-by-side count; and the
gRPC server and Kafka listener threads were not inspected.
